# `1.0.3` → 1.0.4 — One canonical file format

## Summary

Every producer and consumer of a file now speaks one shape. Before this release a file was a
different object depending on which code path produced it: `FileModel` carried
`file_id`/`name`/`metadata`, `FilesystemRecord` carried a `file_type` string whose *value
differed between the local and gRPC backends*, and each module hand-rolled its own dict. This
release introduces **`FileMetadata`** — six fields, one definition — and rewires the filesystem
service, the file history and the setup schema around it.

The format is the payload the front-end file widget already stores in form data, so a
`knowledge_files` field round-trips: what is submitted is what is persisted, and the widget
repopulates itself when the form is reopened.

```json
{
  "id": "files:01m1...",
  "name": "rapport.pdf",
  "type": "FILE_TYPE_DOCUMENT",
  "content_type": "application/pdf",
  "size_bytes": 21923,
  "file_url": "https://.../v1/files/files:01m1..."
}
```

> Breaking changes are marked **(breaking)**. No proto change was required — the wire already
> carried every field; the SDK simply disagreed with it.

---

## Added

### `FileMetadata`, `FileType`, `FileUploadMetadata`

New in `src/digitalkin/models/services/filesystem.py`, exported from
`digitalkin.models.services`.

- **`FileMetadata`** — the canonical six fields (`id`, `name`, `type`, `content_type`,
  `size_bytes`, `file_url`). `FilesystemRecord` now inherits it and adds only what the proto
  `File` message carries beyond them (`context`, `checksum`, `metadata`, `storage_uri`,
  `status`, `content`, `visibility`). Because the extra fields live on the subclass, a record
  placed in a `list[FileMetadata]` serialises to exactly the six — file history stores the
  format, not the content bytes.
- **`FileType`** — a real enum whose values *are* the proto wire names
  (`FILE_TYPE_DOCUMENT`, …). A `_missing_` classmethod coerces the bare name, any casing and
  the prefixed form onto one member, mirroring `Visibility._missing_`, so existing callers
  passing `"IMAGE"` or `"FILE_TYPE_IMAGE"` keep working. An unrecognised value raises rather
  than silently becoming `UNSPECIFIED`. `FileType.from_content_type()` classifies a MIME type,
  replacing a mapping that had been copy-pasted into module code.
- **`FileUploadMetadata`** — the imposed structure for the `metadata` carried on an upload,
  previously an untyped `dict[str, Any]`. Modules needing a stricter contract register their
  own model the way storage collections do:
  `services_config_params = {"filesystem": {"config": {"metadata_model": MyFileMeta}}}`.
  Validation runs before anything touches disk or the wire, and only keys the caller actually
  set are serialised, so validating adds nothing to the payload.

### `knowledge_files_input` — a setup field with declared formats

`src/digitalkin/models/module/knowledge_files.py`. One declaration gives a setup model the file
widget, the allowed-format list and server-side enforcement:

```python
knowledge_files: knowledge_files_input(extensions=[".json"], config=False) = Field(
    default_factory=list, title="Knowledge Files"
)
```

The allowed formats reach the widget as `ui:options.accept` and are checked again on submit,
since the widget's filter is only a hint. A submission carrying no name — a bare id — is not
rejected: the format cannot be judged before the service resolves it.

**Use `config=False`.** With `config=True` the field is stripped by `create_setup_model`, the
persisted setup version loses the file list, and the form reopens empty.

### `FilesystemMixin` helpers

`upload_file` (infers the type from the MIME type), `get_files`, `delete_file`,
`set_visibility`, and `resolve_files` — which backfills a bare-id submission from the stored
record so the persisted entry stays displayable.

## Changed

- **(breaking)** `FilesystemRecord.file_type` → **`FilesystemRecord.type`**, typed `FileType`.
  Comparisons against string literals must become enum comparisons:
  `record.file_type == "FILE_TYPE_IMAGE"` → `record.type is FileType.IMAGE`.
- **(breaking)** `UploadFileData.file_type` → **`UploadFileData.type`**, and
  `update_file(file_type=…)` → `update_file(type=…)`.
- **(breaking)** **`FileModel` removed** from `digitalkin.models.services.storage`;
  `FileHistory.files` is now `list[FileMetadata]`. `FileMetadata.id` accepts `file_id` as a
  validation alias, so rows written by an older SDK still load.
- `FileFilter.file_types` is now `list[FileType]`.
- `update_file` takes a `context: Context` argument, like the other RPCs.
- `digitalkin.services.filesystem` re-exports `FileFilter`, `FilesystemRecord` and
  `UploadFileData`; importing from `…filesystem.filesystem_strategy` is no longer necessary.
- `agentic-mesh-protocol` pinned to `1.0.2`.

---

## Fixed

Four defects the unification exposed, all in the filesystem service:

- **Local and remote disagreed on the type value.** `GrpcFilesystem` returned the prefixed
  wire name while `DefaultFilesystem` returned the bare one, so a record could not be fed back
  into an upload and a literal comparison only ever matched one backend. Callers comparing
  against `"FILE_TYPE_IMAGE"` misclassified every file in local mode.
- **`update_file` addressed the wrong path.** It rebuilt the path from the file *id* while
  uploads write under the file *name*: a content update landed in an orphan file and the next
  read returned the pre-update bytes. A rename with no content raised `FileNotFoundError`.
- **`file_url` went stale after a rename.** `storage_uri` was refreshed and `file_url` was not,
  leaving the public URL pointing at the pre-rename path.
- **`update_file` and `delete_files` ignored the caller's context**, forcing `CONTEXT_MISSIONS`
  regardless. Locally, uploads stamped the setup id as the record context while the gRPC path
  stamped the mission — the record and the bytes disagreed about where they lived.

Each carries a `# TODO(validate)` marker and a `[VALIDATE …]` log line
(`FSCTX`, `FSPATH`, `FSURL`); strip them with `rg "TODO\(validate\)"` once validated in prod.

---

## Migrating

1. `record.file_type` → `record.type`, comparing against `FileType` members.
2. `UploadFileData(file_type=…)` → `UploadFileData(type=…)`; a bare string still coerces.
3. Replace `FileModel` with `FileMetadata` (`file_id=` → `id=`).
4. Any local `FileType` literal, MIME→type mapping or `Filesystem` wrapper narrowing the type
   can be deleted in favour of the SDK enum.
5. On a `knowledge_files` setup field, pass `config=False`.
